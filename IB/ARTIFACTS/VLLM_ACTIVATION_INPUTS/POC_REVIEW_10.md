## Verdict: APPROVE WITH FIXES

The design is implemented as reviewed (captures around the last pass only, gradient through every pass, zero-init adapter on a forked stream, migratable-missing keys, no scalar parameters, `passes_off` panel, unweighted metric, per-example mean-1 weights, bins by cumulative mass with the token-count bins recovered exactly at γ = 0). ## Blockers

**B1 (every arm, at the defaults). `AdaptiveSummaryPooling.bins` builds the bin arithmetic on the CPU when no surprisal is given, then adds it to a CUDA tensor.** `ac_model_utils.py:475`:
```python
ordinal = torch.arange(num_rows, device=surprisal.device if surprisal is not None else None)
```
`device=None` is the default device (CPU; `torch.arange(3, device=None).device` is `cpu` here and nothing in `activation/` calls `set_default_device`). The old code had `device=rows.device`. At `pool_surprisal 0` — the path every existing arm and the six non-pooling arms take — `starts` / `ends` come back on the CPU and `:492` does `starts[:, None] + torch.arange(width, device=rows.device)[None]`: a `[V, 1]` CPU tensor plus a `[1, width]` CUDA tensor raises `RuntimeError: Expected all tensors to be on the same device`. It fires in the first encode of the run (the baseline reporting panel, or the row-position calibration of a deep arm). The CPU tests pass because there the two devices coincide, and the round-5/6/7 digest run (`bitcheck.py`) is CPU as well, so the "bit-identical at the defaults" claim is true on CPU and moot on CUDA.
*Fix*: give `bins` the device explicitly and use it for the ordinal in both branches — `def bins(self, length, num_rows, surprisal=None, device=None)` with `ordinal = torch.arange(num_rows, device=device if device is not None else (surprisal.device if surprisal is not None else None))`, called as `self.bins(length, num_rows, surprisal, device=rows.device)` at `:490`; `_record_pool_diagnostics` (`ac_model.py:1011`) passes a surprisal and needs no change. Any equivalent (e.g. `rows.device` threaded through) is fine; the invariant to restore is "the token-count path is `torch.arange(num_rows, device=rows.device)` as before".

**B2 (the six `pool_surprisal` arms). `_content_surprisal` hands a 3-D tensor to `head_logits`, whose CUDA path is `torch.mm`.** `ac_model.py:991`:
```python
logp = F.log_softmax(head_logits(hidden[:, start:end], head), dim=-1)
```
`hidden` is `[B, longest, d]` in the side base's dtype (bf16 on the nodes). `head_logits` (`agent_training_utils.py:321–331`) takes the `F.linear` branch only when the states are not on CUDA or the dtypes differ; with bf16 states and a bf16 head on CUDA it runs `_HeadMatmul.apply`, whose forward is `torch.mm(states, weight.t(), out_dtype=torch.float32)` (`:310`) — `mm` requires matrices (`RuntimeError: self must be a matrix`, confirmed here on the 3-D shape). The tiny CPU fixture is fp32 and takes the `F.linear` branch, which broadcasts, so `test_pool_surprisal_encoder_and_training` cannot see it. A32SP / A32SPKVTA / NSP and their twins would die in the first encode.
*Fix*: flatten the chunk before the head and restore the shape after it:
```python
states = hidden[:, start:end].reshape(-1, hidden.shape[-1])
logp = F.log_softmax(head_logits(states, head), dim=-1).view(len(pending), end - start, -1)
```
(the gather at `:992` is unchanged). While there, consider chunking by *flattened* tokens rather than by 256 positions × B rows — the fp32 logits chunk is `B × 256 × 151,936 × 4 B ≈ 155 MB × B` plus the `log_softmax` copy; at micro-batch 3 (one part per example) that is ≈ 1 GB transient, fine on the 80–96 GB cards but proportional to B, and the flattening makes a fixed 256-token chunk trivial. Not required for the launch.

Neither fix changes a CPU-observable value; the digest and the eight tests stay as they are. Because no GPU test exists for either branch, I recommend (not a condition of the approval) running the `S` smoke arm once with `encoder_passes 2, pool_surprisal 1, rare_weight 1` before submitting the twelve arms: a two-minute job that executes every new branch (surprisal forward, mass bins, the bias mask under autocast, the second pass, the `passes_off` panel, the rare-token panel) on the real dtype and device.

**(4) `pool_surprisal`.** `mass_bins` (`ac_model_utils.py:436–451`): float64 cumulative sum, `searchsorted(right=True)` for the starts and `searchsorted(right=False) + 1` clamped for the ends. With a uniform mass this is `floor(jN/V)` / `ceil((j+1)N/V)` — the token-count bins — and the test checks seven `(N, V)` pairs including `V > N`. On the "exactly one bin" question: the *existing* floor/ceil bins already overlap by one token at every fractional boundary (N = 10, V = 4 gives `[0,3) [2,5) [5,8) [7,10)`), so the invariant was never "exactly one" but "every token in at least one bin, at most two, ordered, no gap"; the mass bins keep exactly that (checked by the test on random masses, and here on a single 100-nat spike: bins `[0,11) [10,11) [10,11) [10,11) [10,13) [12,25) [25,38) [37,50)` — the spike token alone fills four rows, which is the feature). Rows per part are `num_view_rows` as before. γ = 0: `surprisal_bias is None` → the `bins()` token-count branch and the old attention call, no surprisal computed. The width bound `(1+γ)·N/V + 2` holds because a bin's mass is at most `T/V` plus its two boundary tokens, each of mass ≤ `1 + γ·s_max/mean`; at γ = 1 that is the "2 × uniform + 2" the note states only when `s_max ≤ 2·mean` — for a heavy spike a single bin can be wider (the spike token's mass is `1 + γ·s/mean`, so a bin holding it plus its neighbours can exceed the bound by the spike's share). The gather stays bounded by `N` in any case and the test's "widest bin ≤ 2 × uniform + 2" passed on its material; on real passages `s_max/mean` is 5–10, so expect `pool_width_max` above the note's bound occasionally. Harmless (the diagnostics show it), but the docstring's bound is not strictly true.

*The pooling bias on CUDA/bf16 — it will run.* The call at `:507–508` is `nn.MultiheadAttention(batch_first=True)` with query `[V, 1, d]`, key = value `[V, width, d]`, `key_padding_mask` a float `[V, width]` (0 / −inf) and `attn_mask` a float `[V·heads, 1, width]`, `need_weights=False`. Under the encoder's CUDA autocast the inputs are the outputs of `self.norm` (LayerNorm is on autocast's fp32 list), so `normed.dtype` is fp32 and both masks are built in fp32 — the same type, so `_canonical_mask` neither converts nor warns; `F.multi_head_attention_forward` accepts a 3-D `attn_mask` of exactly `(bsz·num_heads, tgt_len, src_len)`, expands the padding mask to the same shape in the same (row-major over batch, then head) order the `[V, heads, 1, width].reshape(V·heads, 1, width)` bias uses, and adds them (`torch/nn/functional.py:7000–7013`); with `need_weights=False` it views the merged mask as `(bsz, num_heads, 1, src_len)` and calls `scaled_dot_product_attention` (`:7064–7079`). The in-projections run in bf16 under autocast; SDPA accepts a float mask whose dtype differs from the bf16 query (validated here: bf16 q/k/v with an fp32 mask runs), and under autocast it is cast to bf16 anyway; −inf is representable in bf16 and no row is fully masked (every bin is nonempty), so no NaN. Emulated here with `torch.autocast("cpu", bfloat16)` on the module in train and eval mode: runs, fp32 output, gradient reaches `surprisal_bias`. The fast path is never taken (query is not key). Batch > 1 and parts of different lengths are outside the module (it is called per part); `V > N` works (tested). *The extra no-grad side forward*: one right-padded base forward per uncached part with the adapter disabled (`lora_name=None`), no mask (causal), no checkpointing, before the mixer and before any capture context; ≈ a third of a side training pass plus the LM-head readout (≈ +15 % of a forward at 2 k tokens); cached by a SHA-256 of the part's ids as a CPU fp32 tensor (8,192 parts × 2 k × 4 B ≈ 65 MB; cap 100 k entries), so the 1-epoch arms pay once per training part and once for the held-out parts across the ≈ 9 panels. Correct under micro-batching: right padding after real tokens changes nothing under causal attention and the causal GDN recurrence (tested on a batch of two on CPU). Two GPU-only caveats, neither blocking: (i) bf16 kernels on a padded batch can differ from the single-part forward in the last bits, so a cached `s_t` depends on which batch computed it first — a ~1e-3 relative jitter that can flip a boundary token between two adjacent bins; (ii) the transient logits are `B × 256 × vocab` fp32 twice (see B2's chunking remark). The placeholder runs of nested parts are set to the mean of the real tokens (`:995–1002`), but the tokens *after* a run were conditioned on pad ids in the forward — an approximation with no bearing on the recon arms (no nested parts).

## Findings

**1. BLOCKER — B1** (`ac_model_utils.py:475`): the token-count `bins()` path allocates on the default device; on CUDA the default path crashes at the first encode of every arm. Fix above.

**2. BLOCKER — B2** (`ac_model.py:991`): 3-D states into `head_logits` → `torch.mm` on CUDA; the six `pool_surprisal` arms crash at the first encode. Fix above.

**3. NOTE — `eval()` on surprisal runs requires stored references.** `_target_surprisal` raises when the item's no-context reference is missing (`ac_model_training.py:1297`); every call site in the bench is covered (training, reporting, validation and the post-training seen subset are all stored in `train()`), but a later `eval()` on new items — the `clean_panel.py` style re-scoring, or a fresh trainer over a saved checkpoint — must either store references first (`_store_teacher_targets(..., lora=None)` on the penalty examples, as `train()` does at `:604`) or run with `rare_weight 0` on a `pool_surprisal 0` model config. Worth one line in the round document; a `{}` fallback with a warning would also be defensible, but the loud error is the safer default for a run.

**4. NOTE — the gate-group guard is `numel() == 1`.** `surprisal_bias` is `[mixer_heads]`; with `mixer_heads 8` on every arm it lands in group 0 as intended. A future config with one mixer head would put it in the gate group at `gate_lr`. Not an issue for this round.

**5. NOTE — the width bound in the docstring is conditional.** "At most `(1 + γ) × uniform + 2`" holds when the heaviest token carries ≤ `(1 + γ)` units of mass, i.e. `s_max ≤ mean(s)` at γ = 1; a heavy spike can make one bin wider (its neighbours ride along) — see the spike example in (4). The gather is still bounded by N and the `pool_width_max` trace shows it; read that trace before comparing memory across arms.

**6. NOTE — the first encoder-trace entry mixes the baseline completion samples' encodes.** `_sample_completions` runs the encoder in training mode after the baseline drain (`:684` after `:683`), so its parts' `refine_rms` / `pool_*` values sit in the store until the first update's `_absorb` — the same contamination the `cosine` / `delta_rms` diagnostics have had since round 3, and at init `refine_rms` is 0 for every part anyway. Cosmetic.

**7. NOTE — cost line for the arms.** Passes 2: side forward and backward ×2 (the note's ≈ +30–40 % step time on the 1/32 arms); `pool_surprisal`: ≈ +0.4 side forward per training part (once) plus the held-out references (one base forward per reporting / validation item, once per call); `rare_weight`: free. The `passes_off` panel re-encodes the reporting items at one pass per panel (≈ half the reporting evaluation's encoder cost). If A32W ran close to the 27,000 s budget, A32P2 / A32KVTAP2 may truncate; compare at matched update counts.
