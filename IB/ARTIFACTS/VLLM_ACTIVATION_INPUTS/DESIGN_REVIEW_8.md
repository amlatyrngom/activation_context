# Design review 8 — `ROUND8_ENCODER_PLAN.md` (iterative encoder + lexical-anchor loss)

Reviewed against the plan (01:20 UTC 09-17), results findings 11 and 16–19, the ledger to 01:13 UTC (A32KVTF / NKVTF exact, A32KVTA −0.018/−0.022, four distillation arms null), review 7, and the code the plan extends: `activation/ac_model/ac_model.py:714–883` (`_encode_prepared_batch`), `ac_model_utils.py:436–487` (summary pooling, `RowHead`), `hf_utils.py:357–407` (side captures), `loaded_model.py:485–524` (`decoder_forward`), `ac_model_training.py:400–433, 531, 575–585, 683–686, 1343–1413, 1564–1582` (examples, stored references, optimizer groups, loss assembly, batched SFT). No code for round 8 exists yet; this is a judgement on the design. Read-only.

## Verdict: SOUND WITH CHANGES

Feature A (iterative encoder) is sound as a proof of concept in the form written — it starts exactly on the control line, works through the hybrid model's linear-attention layers where a bidirectional mask could not, and feeds back the quantity the reader actually consumes — but it needs one correctness fix for the K/V-transfer arm (the side captures record the *first* forward and ignore the second), two within-run readouts without which a null is undiagnosable, and an honest cost line. Feature B (lexical anchor) as specified cannot supervise the two failure modes it is built for: a bag of tokens is order-blind, and the documented misses are order errors on pieces the model already has (`_render_for_list_str` → `_render_list_for_str`) and digit substitutions inside numbers (1798 → 1778), where a unigram-rarity rule never marks the digits rare at all. B must be re-specified (per-row targets, surprisal-defined rare set) and read against a zero-parameter control that supervises the same tokens through the reader itself (terminal-loss reweighting). The most impactful encoder-side lever the findings point at is not in the plan: putting the row budget where the entropy is (surprisal-weighted pooling), proposed below.

## Blockers (fold in before the arms run)

**B1. The side captures must be opened around the last pass only, and the pass-invariant targets refused.** `capture_kv_rows` records once per forward and ignores later forwards while its context is open (`hf_utils.py:366–370`: `if store: return`), and `capture_layer_input_rows` does the same (`:395–397`). `kv_transfer` forces `intervention_source side_layers` (`ac_model.py:190–191`), so both contexts are open on the transfer arms (`:780–793`). If the implementer wraps the pass loop in the existing contexts, A32KVTAP2 silently ships pass-1 K/V (and pass-1 side states to the correction head) next to pass-2 rows — a different experiment from the one in the table, and an undetectable one, since the `len(...) != batch_size` checks at `:795–796` still pass. Enter the capture contexts for the final pass only (or clear the records between passes) and add a test that the captured K/V equal a standalone forward over the pass-2 inputs. Also refuse `encoder_passes > 1` with `kv_transfer_full` and `cross_attention`: their spliced content comes from content positions (`_transfer_span` `:885–891`, `hidden[row, :end - num_rows]` `:815`), which are pass-invariant under causal attention, so those arms would cost 2× and change nothing.

**B2. Re-specify the anchor target before implementing it; as written it does not touch the failure mode.** Three defects, each sufficient on its own:
- *Order.* Finding 11's identifier errors are recombinations of pieces the model already produces (`_render_for_list_str` → `_render_list_for_str`, reused consistently across six calls): the multi-hot bag of both strings is identical, so the loss is already zero on them. Numbers: Qwen's pre-tokeniser splits digits one per token, so 1798 → 1778 changes one element of a bag of the most frequent tokens in the material.
- *The rare rule.* Unigram frequency "below a quantile of the vocabulary mass" excludes single digits, `_`, `str`, `list`, `for`, `render`, `id` — the pieces identifiers and numbers are made of. What is lost first is not globally rare tokens but tokens that are *unpredictable in context*. That quantity is already stored for every training example at zero cost: the arms run `penalty_ref stored` (`arms.json`), every example carries a no-context reference (`ac_model_training.py:430–433`) and `_store_teacher_targets(..., lora=None)` (`:531`) stores the base's log-prob of every target token, which for the reconstruction task is every passage token. Define rare as `−log p_base(t) > τ` (τ ≈ 3 nats; log the share, expect 10–20 %), optionally unioned with token classes (digit, identifier piece) as `deviations.py` classifies them.
- *Mean over rows.* A single head over `mean(rows)` can be satisfied by one row (or a shared subspace) holding the whole bag; the reader needs the identifier in the row that covers its span. Use per-row targets: row j's positives are the rare tokens in its pooling bin (`starts/ends` at `ac_model_utils.py:449–453`; expose the bin arithmetic as a function so the trainer and the pooling cannot drift apart). That also gives coarse order for free and costs V × C logits, trivial.
And add the control the plan is missing: **terminal-loss reweighting on the same rare set** (`rare_token_weight` β: per-token weight `1 + β·[rare]` in `_chunked_sft_tokens` `:1564–1582`, applied to the per-token cross-entropy at `:1379–1384`; metric unweighted; bit-identical at β = 0). It is order-aware, supervises the rows *through the reader's own fetch* (so "satisfied" means "readable"), and has no head to overfit. The plan's own rationale for B ("identifiers are few tokens among many, so the terminal signal is weak") is exactly what reweighting fixes. If A32AN cannot be made per-row and surprisal-defined in time, drop A32AN / A32P2AN and run the reweighting arm instead; if both run and the reweighting arm is at least as good, the head is unnecessary.

**B3. Within-run readouts for A, or a null cannot be read.** Findings 15 and 18 are the precedent: a zero-init path can stay at zero, or grow and be driven back. Two cheap readouts: (i) a `passes_off` panel — the reporting items scored with `encoder_passes` forced to 1 (rows from pass 1), the `deltas_off` machinery (`:527–532`, `:1041`); held − passes_off is the second pass's worth at inference, the only cross-run-noise-free number at midi size (finding 13); and (ii) a `refine_rms` trace: RMS of `refine(prev)` relative to the summary input it is added to, per update, like `intervention_delta_rms` (`_record_diagnostic` `:898–901`). Report the pass-1 → pass-2 row cosine on the panel as well. For the anchor arms the `rare_token_accuracy` panel must exist for the *controls* too: it can be computed offline for every finished arm — the panels already store every target token's log-prob (`_evaluate` `:1060–1061`, `target_logp` per item) — so write it as a post-hoc script over `result.json` like `clean_panel.py`, not as a new trainer widget, and run it on A32W / A32X / A32KVTA / W16L first so the baseline number is known before the arms finish.

**B4. Bit-identity and checkpoint compatibility, the round-5/6/7 way.** `refine_adapter` and `anchor_head` are registered only when configured (`encoder_passes > 1`, anchor on), drawn from a forked generator so the mixer, heads and adapters draw the sequence they drew before (`ac_model.py:255–262`); `load` must treat `refine_adapter.*` / `anchor_head.*` as migratable-missing when a K16 / K16r1 input-only checkpoint is loaded (extend the `deep_keys` set at `:976` and the summary check at `:961–970`; record `encoder_passes` in the saved summary and refuse a mismatch that changes meaning); nothing in the new modules may be a scalar parameter or it lands in the gate group (`gate_parameters = numel() == 1`, `ac_model_training.py:578`); `stats.side_tokens` counts a part once, not once per pass (`:877`), or the throughput widget misreads. Run `bitcheck.py` (POC_IMPLEMENTATION_7 §bit-identity) on the base tree and the worktree with the defaults, plus a passes-2 configuration whose rows must equal the passes-1 rows at init to bf16 tolerance (the mathematical identity below).

## Suggestions

### (1) Soundness of the iterative pass

What pass 2 adds, precisely. In pass 1 summary j at layer l sees the content and summaries ≤ j at layer l−1: rows *do* coordinate across depth (32 layers), but never see rows > j, and never see any row's *final* state — only its layer-matched one. Pass 2 feeds `rows_1` (post-final-norm, `hidden` at `:803`) back to layer 0 at the same positions, so row j now reads the final states of rows ≤ j, and the computation over the row positions is effectively 64 layers deep with shared weights. Under the causal mask row j still does not see rows > j; the plan's "each row reads what the other rows captured" holds for the predecessors only. Two cheaper forms give the "all rows" property in one pass, and neither is a drop-in:
- *Bidirectional attention among the summary positions* (custom 4D mask through `decoder_forward`, zero extra compute): possible only at the 8 full-attention layers — the GDN layers are a causal recurrence and cannot be masked. It also moves the rows off the control line at step 0 (the side LoRA has never seen a non-causal block), which spends part of the 1,024-update pass recovering, exactly what cost the distillation arms (ledger 00:18).
- *A second block of V summary positions after the first* (N + 2V tokens, rows = the last V): the second block sees the whole first block layer by layer, works through the GDN layers, costs V tokens instead of a forward — but its rows are new positions with a different context and are likewise not at control at init.
The plan's form is the only one that is *exactly* pass 1 at init (`refine` zero-init, `summaries_1 + 0`), which is what a 0.004-floor read from a warm start needs. Keep it for the POC. The correct cost line: the second forward recomputes the N content positions whose states are identical to pass 1 (causal: content never attends to summaries), so ≈ 97 % of pass 2 is redundant — training side cost ×2, write-time cost ×2. The production form is a cache-continued pass over the V summary tokens only (`decoder_forward` runs `use_cache=False`, `loaded_model.py:520`; the K/V cache plus the GDN recurrent state after the content, snapshotted before `summaries_1`, would have to be graph-attached under non-reentrant checkpointing — real work, not for this round). Say so in the plan; do not call the extra pass "a fraction of the step" without the multiplier.

Gradient at init: with `down` = 0, `rows_1` receive no gradient from pass 2 (the LoRA-style bootstrap; `refine.down` itself does, ∝ `up(rows_1)`), so pass 1 is trained only through the shared `summaries_1` input until the adapter grows. That is fine, but it is why B3's `refine_rms` trace is needed. One design choice to make explicit: whether `refine(prev)` is added before or after `input_scale` (`:762`), and that it is *not* unit-normalised (the finding-18 lesson: lora style, no unit-RMS, no learned scale). Position ids and the padding mask are unchanged (replacement, same positions), so the K/V transfer's pre-RoPE capture is unaffected once B1 is done.

Checkpointing and memory: two `decoder_forward` calls each under their own `checkpoint_adapter_scope`, both frames retained until backward — ≈ 32 × B × S × d × 2 B ≈ 1 GB per pass at micro-batch 3 and 2,000 tokens, fine; the reader's activations dominate. The captured K/V slices are graph-attached views into the last pass's frame, the same shape round 6 matched to 1e-6; ship the checkpointed-vs-uncheckpointed gradient test for the side LoRA, `refine_adapter` and `target_head` under passes 2 (both branches run in one job at `ckpt_min_tokens 1700`).

Expected size of the effect: a second pass changes how the fixed per-row capacity is *allocated*, not the capacity; the pooling bins are an ordered partition (`:449–453`), so the assignment problem the plan describes is mild. A 1/32 win of 0.005–0.015 is plausible; 0.05 is not. Read `passes_off` before believing either.

### (2) The anchor loss (beyond B2)

- *Loss form.* With ~10–50 positives against 2,048 negatives a BCE is dominated by "push everything down"; a sampled softmax (−mean over positives of log softmax over the candidate set) or a positives/negatives-balanced BCE is better conditioned at no extra cost.
- *Head init.* Rows after `target_head` already live in the reader's embedding space (tied embeddings, skip-init head `ac_model_utils.py:470–478`), so `E · row` is meaningful at init. Make the head identity plus a zero-init residual FFN (the `RowHead` skip pattern) rather than a random d → d; a random projection makes the initial gradient into the rows noise, a zero-init one makes it zero.
- *Weight and schedule.* 0.1 constant is a reasonable first value; do not hold a high weight early (the distillation lesson). Log the anchor term and the terminal loss on the same clock; the arm's read is the *unweighted* held loss at the end.
- *Overfit risk.* A separate head means the rows can satisfy the anchor in a subspace the reader does not read; round 7 is the precedent (the rows became teacher-like, the terminal loss did not move). The reweighting control in B2 is the guard: if the head arm beats the control, the head adds something; if not, it was capacity spent elsewhere.
- Positives come from the *side* token ids of the bin (`PreparedPart` ids, the side tokenisation of the part), while the rare set is defined on target tokens; side and reader share the tokenizer on every arm here (same base model), so the ids agree — assert it once at build time.

### (3) Are these the most impactful encoder-side levers? Partly. Two stronger ones, both vLLM-neutral

The findings say: the reader is not the limit (ceilings 0.000), the row budget is, and what the rows drop first is high-surprisal content. Neither feature in the plan changes *where* the budget goes; both change how well a fixed, uniform allocation is filled. The lever that addresses the finding directly:

**Alternative 1 — surprisal-weighted summary pooling (spend the rows where the entropy is).** Mechanism: per side content token a scalar s_t = the base's no-context surprisal of that token (free from the stored penalty reference for training, `:531`; at write time one chunked `lm_head` readout on the side pass's content states — bf16, gold log-prob only, ≈ 5–10 % of the side forward). `AdaptiveSummaryPooling` (`ac_model_utils.py:446–464`) bins by *cumulative surprisal mass* instead of token count — `starts/ends` from the CDF of s_t, so a row covers an equal share of the passage's entropy, identifier-dense regions get more rows and boilerplate fewer — and the pooled query's attention logits get a zero-init bias `γ · s_t`. Row count per part is unchanged (the ratio keeps its meaning; not a sidecar); bit-identical at γ = 0 with uniform bins, so it starts on the control line. The plan's "not in this round" excludes adaptive *placement* of rows in the reader; this is adaptive *content* in the writer and needs no reader change. Expected: the largest of the three at 1/32, because it is the only one that moves bits from cheap tokens to expensive ones.

**Alternative 2 — surprisal-weighted terminal loss (the zero-parameter version of B).** Mechanism: per-token weight `w_t = 1 + β · clamp(s_t / s_max, 0, 1)` (or `1 + β·[rare]`) on the per-token cross-entropy at `ac_model_training.py:1379–1384`, normalised by Σ w over the update; metric unweighted; β = 0 bit-identical. Order-aware by construction (teacher-forced next-token), supervises identifiers through the reader's own fetch, no head, no bag, twenty lines. It is B2's control and, if the head is dropped, B's replacement. Risk: over-weighting lifts the loss on common tokens; the unweighted held panel decides, and β ∈ {1, 3} is the sweep.

### (4) The arms table

Bases and twins are right (A32W 0.340 / A32X 0.322 on K16r1 / K16; A32KVTA 0.322 for the transfer line; WCa 0.130 at 1/16). The 0.01 criterion is 2.5× the only measured floor (0.004 at 1/16, WCa vs WCb); no 1/32 replicate pair exists, so require in addition that the sign agrees on both inits and that `passes_off` (or the anchor control) shows the same ordering within the run. Changes:
- **A32KVTAP2** is the highest-value line (the second pass rewrites the K/V the reader fetches, which is the channel that already wins); it depends on B1.
- **A32P3** before A32P2 has shown anything is a wasted slot: run it only if A32P2 is ≥ 0.005 below A32W; give its slot to **A32RW** (terminal reweighting, β = 2, alternative 2).
- **A32AN** only in the per-row, surprisal-defined form (B2); **A32P2AN** after the singles, not with them.
- Add **A32SP** (alternative 1) if it fits the round; it is the arm most likely to move the number.
- **NP2** (1/16) is a "does it hurt where rows are not starved" check; low priority, keep last.
- Every arm and its control gets the post-hoc `rare_token_accuracy` (B3), split by digit / identifier-piece / other so the readout matches finding 11.

### (5) Implementer checklist (in addition to B1, B4)

- `encoder_passes` and the anchor keys on `ActivationContextModelConfig` (`ac_model.py:100–156`) with `__post_init__` validation (passes ≥ 1; passes > 1 refused with `kv_transfer_full` / `cross_attention`); the anchor *weight* is a trainer setting (`ActivationContextTrainingConfig`, `ac_model_training.py:70–131`), the anchor *head* a model module — decide which config owns the on/off switch and keep `load` consistent (a checkpoint saved with the head must load into a model without it: drop the keys with a message, as the migrate path does in reverse).
- The pass loop lives in `_encode_prepared_batch` between `:778` and `:801`: build `inputs_embeds` for pass k from the pass-1 `sequences` plus `refine(unit_rows(rows_{k-1}))` on the summary slice only; the mixer, pooling and `summaries` (`:749–762`) run once; `run(...)` checkpointing of the mixer is untouched; `enabled` (`:775–777`) applies to every pass.
- Optimizer: the refine adapter and anchor head go in group 0 at `learning_rate_ac` (`:579`); no new group; `trainable_parameters` (`ac_model.py:606–611`) picks them up by `requires_grad`.
- Anchor term: computed in `_batch_loss` from `outputs[i].input_embeds` (`:1359`, fp32 before the `.to(dtype)`) and added into the loss sum at `:683–686` with its own totals entry, like `distill`; the per-row targets built in `build_example` and cached on `_Example`; negatives drawn from the trainer's seeded RNG (resume-safe).
- Tests on the tiny hybrid fixture (`activation/tests/test_interventions.py`): passes 2 == passes 1 rows at init; last-pass capture equals a standalone forward; checkpointed vs plain gradients under passes 2; anchor off → no keys, no group, same digest; anchor term equals a naive computation on one example.
- Rollout mode runs the passes too (`encode_batch` under no grad): the agent-side write cost doubles per uncached part; note it in the plan's cost line.

## Alternatives (summary)

1. **Surprisal-weighted summary pooling** — bins by cumulative base surprisal, zero-init surprisal bias on the pooling attention; s_t stored for training, one chunked lm_head readout at write time; rows per part unchanged; γ = 0 bit-identical. Targets *where* the 1/32 budget goes; the finding's first-order lever.
2. **Surprisal-weighted terminal loss** — per-token weights on the SFT cross-entropy, metric unweighted, β = 0 bit-identical; order-aware, reader-faithful, no module. The control for B and its cheaper replacement.

## Verdict: SOUND WITH CHANGES

Blockers: B1 side captures around the last pass only, pass-invariant targets refused — B2 anchor re-specified (surprisal-defined rare set from the stored base reference, per-row targets from the pooling bins) and read against terminal-loss reweighting on the same tokens — B3 `passes_off` panel + `refine_rms` trace, post-hoc `rare_token_accuracy` on the controls first — B4 state-dict / RNG / migrate / gate-group discipline with the digest run. Feature A proceeds as written once B1/B3/B4 are in; feature B does not run in its current form.
