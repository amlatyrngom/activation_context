## Findings (by severity)

### 1. HIGH — `generate(interventions=...)` is rejected by HF; the sampled-completion path as planned cannot run

- **What is wrong.** §5 (`generate_with_interventions`) says the helper "passes `interventions=` through `generate` (HF forwards unknown kwargs to `forward` each step)". It does not. `GenerationMixin._validate_model_kwargs` accepts only names in the signatures of `prepare_inputs_for_generation`/`forward` or in `TransformersKwargs.__optional_keys__`; `**kwargs` in the signature does not whitelist arbitrary names. Probe on a tiny `Qwen3ForCausalLM`: `generate(inputs_embeds=…, interventions=[payload])` → `ValueError: The following model_kwargs are not used by the model: ['interventions']`.
- **Evidence.** `.venv/lib/python3.14/site-packages/transformers/generation/utils.py:1614-1665`; `activation/ac_model/ac_model_training.py:850` (the call site is `peft_model.generate(inputs_embeds=…, do_sample=False, use_cache=True)`).
- **Change.** In `generate_with_interventions`, bind the payload for the duration of the call by wrapping `peft_model.base_model_prepare_inputs_for_generation` (the instance attribute PEFT's own `prepare_inputs_for_generation` calls, `peft/peft_model.py:2233-2235`; PEFT's `generate` installs/restores it itself at `:2212/:2227`) with a closure that adds `model_inputs["interventions"] = payloads`, restored in `finally`. This is a per-call binding, no model-global field, and it never passes through `generate`'s kwargs. Test: a hook counter shows the payload present at prefill and absent/ignored at every decode step; the `ValueError` path is never hit.

### 2. HIGH — the "cached vs `use_cache=False`" generation gate is vacuous on HF 5.15.1

- **What is wrong.** §5 test 6 and §2 (M2 "cached == no-cache") rely on `generate(use_cache=False)` as the no-cache oracle. Probe: with `use_cache=False`, decode steps still arrived at the layers as single-token forwards with a cache of length 6 then 7 (hook saw `(offset, S)` = `(0,6), (6,1), (7,1)`), i.e. HF still ran incremental decoding; nothing recomputed the prompt, so the test cannot detect re-injection or a wrong offset.
- **Evidence.** Probe output on tiny Qwen3; `generation/utils.py:1962` only skips cache *preparation* for `use_cache=False`, the model still builds a `DynamicCache` (`modeling_qwen3_5.py:1163-1164`).
- **Change.** Replace the oracle with a manual greedy loop: at each step run `decoder_forward(full_prefix_embeds + generated-token embeds, interventions=[full payload], use_cache=False)` and take the argmax; assert the ids (and the logits at the last position, within bf16/fp32 tolerance) equal `generate_with_interventions`'s cached output. Keep the hook counter assertion (delta rows applied exactly once, at prefill only).

### 3. HIGH — the POC cannot tell whether the deltas are used: scales are pinned by construction and the only control removes rows and deltas together

- **What is wrong.** §3 "Reading the result" says "scales that never left 1 % says the reader ignored the deltas". With ND's grouping (no gate group, AC rate 1e-4, cosine over 1,024 updates) Adam moves a scalar by about its rate per step, so a delta scale can move at most ≈ 0.05 absolute — the trainer's own comment on the row scale (`ac_model_training.py:504`) documents that this takes ~1,500 steps for a 15× change. `DeltaHead` output is `scale · unit_rows(ffn)`, so delta *magnitude* is essentially frozen at the calibrated 1 % for the whole run whether or not the reader uses the direction; the flat trajectory carries no information. The reader LoRA can still amplify a used direction, so the deltas are not useless — but the planned readout is. The no-context floor (§2 "content-removal control") strips the parts, which removes the input rows *and* the deltas (`build_example` → `strip_ac_parts`, `ac_model_training.py:379-382`), so it cannot attribute anything to the deltas specifically. §6 Q2's "read the scale trajectories" has the same flaw.
- **Change.** (a) Add an eval-only `deltas_off` panel to `_evaluate`/the bench reporting set: the same held items with the input rows kept and the payload replaced by `None` (one flag on `_assemble_student`), evaluated at every panel next to `held`/`wiki`/`no_context`. `held − deltas_off` is the delta contribution; it costs one extra panel pass, is deterministic and needs no training-path change. (b) Keep the head gradient norms and applied-delta RMS in the trace, but state in §3 that the scale trajectory is expected to be flat at ND's grouping. (c) Pre-register `NDIg` (delta scales in their own gate group, shared parameters unchanged, so pairing with NDC holds) as the second run rather than "obvious if the scales look pinned". (d) Note that joint clipping (`clip_per_group=False`) lets the head gradients change the clip factor of the shared parameters in NDI; report `grad_norm_ac` beside the trace so a divergence can be read.

### 4. MEDIUM — the pairing proof (`initial_hash`) and the head RNG isolation are not implementable as written

- **What is wrong.** (a) `parameter_hash` hashes every tensor of `ac.trainable_parameters()` plus the reader LoRA (`run_recon.py:169-174`); `trainable_parameters()` returns an unnamed list (`ac_model.py:252-257`). With heads present, NDC's and NDI's `initial_hash` differ by construction, so the §3 promise "`initial_hash` over the shared parameters must match" is false without a bench change. (b) §3 says the heads are initialised "from a separate `torch.Generator` seeded with `seed ^ 0x_DEEP`": `nn.Linear.reset_parameters` takes no generator, `ActivationContextModelConfig` has no seed field (`grep seed ac_model.py` is empty), and `0x_DEEP` is not a hex literal. Construction order matters: `register_ac_model` builds `ActivationContextModules` before the side and reader LoRA are injected (`module_manager.py:140`, then `ac.prepare()`/`ensure_lora(READER)` in `run_recon.py:277`), so any extra draw in `__init__` shifts both LoRA initialisations.
- **Change.** Build the heads inside `with torch.random.fork_rng(devices=[]): torch.manual_seed(torch.initial_seed() ^ 0xDEE9)` (`initial_seed()` reads the seed set by `harness()`'s `manual_seed` without drawing; `fork_rng` restores the CPU stream). In the bench, hash by name: `parameter_hash` skips `delta_heads.*` (and the new buffers) and `result.json` gains `deep_hash` over the heads. Test: zero-mode and deep models built after the same `manual_seed` have identical shared state dicts and the next `torch.rand(1)` is identical.

### 5. MEDIUM — zero mode must not change `modules.state_dict()` keys

- **What is wrong.** §4 says the checkpoint "gains only `interventions: {"layers": []}`-style fields" and "no changed checkpoint keys"; §5 registers `intervention_layers`, `intervention_calibration`, `interventions_calibrated` as buffers on `ActivationContextModules` and test 2 accepts "keys unchanged except the new buffers". `load()` uses strict `load_state_dict` (`ac_model.py:496`), so a checkpoint written by the pre-change code (every existing arm, K16's epoch-2 checkpoint that §2 wants to migrate later) would fail to load into the new zero-mode model with missing keys.
- **Change.** Register the buffers only when `intervention_frequency > 0` (or keep calibration in the checkpoint dict beside `"config"`, not in `modules`). Add to test 2: a checkpoint saved by the tag's code (fixture generated once from the worktree) loads into the new zero-mode model, and the new zero-mode model's `state_dict().keys()` equals the old one's.

### 6. LOW — hook mechanics: confirmed, three details to pin down

- **Confirmed by probe** (tiny Qwen3, `use_reentrant=False`): a forward pre-hook with kwargs receives `interventions` in the layer kwargs (`modeling_qwen3_5.py:1199-1208` passes `**kwargs` into every layer with `hidden_states` positional); under gradient checkpointing the hook fires twice per layer (forward + recompute, via `partial(super().__call__, **kwargs)` in `modeling_layers.py:110`), the delta gradient equals the non-checkpointed one exactly (max diff 0.0), and two pending checkpointed forwards with different payloads give distinct finite gradients. `cache_position` is **not** in the layer kwargs (`None` in the probe); `past_key_values.get_seq_length()` is the right offset and works on the hybrid cache (linear layer 0 resolves to the first attention layer, `cache_utils.py:1485-1497`; probe on tiny Qwen3.5 saw 0/6/7).
- **Pin down.** (a) Locate layers as `text = decoder.language_model if hasattr(decoder, "language_model") else decoder; text.layers` — `Qwen3_5VisionBlock` is also a `GradientCheckpointingLayer` and must not be hooked; `get_decoder()` returns `Qwen3_5Model` for the 4B checkpoint (`loaded_model.py:504`). (b) Add out of place (`new = hidden.clone(); new[b].index_add_(0, idx, delta)`): an in-place add on the layer input is the previous checkpointed layer's saved output and trips the version counter. (c) Return a new kwargs dict without `interventions` rather than relying on `pop` (works today because `partial` and `_call_impl` rebuild the dict, but say so).
