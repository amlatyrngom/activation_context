Explainer · Attention Matching (Zweiger, Fu, Guo, Kim · arXiv 2602.16284)

Attention Matching, simply: shrinking a document's key/value cache without training

The model reads a long document once and keeps one key and one value per token, at every layer and head. Attention Matching replaces those T entries with t ≪ T new entries plus one extra number per entry (a bias β). They are chosen so that any later query gets the same answer from the document as before. Everything is fit with plain least squares in seconds to minutes, not hours of gradient descent.

1. The one idea: a document answers a query with two numbers

Take one layer and one key/value head. A query \(q\) looks at the document's keys \(K\) (T rows) and values \(V\). From the document's point of view, everything the query gets is captured by two quantities:

  • What the document says: its own attention output, normalized over the document only: \[\text{out}(q) = \frac{\sum_j e^{q\cdot K_j}\,V_j}{\sum_j e^{q\cdot K_j}}\]
  • How loud the document is: its attention mass, the softmax denominator it contributes: \[\text{mass}(q) = \sum_j e^{q\cdot K_j}\]

When the document sits next to other tokens (the question, the answer being written, other documents), the real attention output is just a mass-weighted mix of each block's own output:

\[\text{attention}(q) = \frac{\text{mass}_{\text{doc}}\cdot\text{out}_{\text{doc}} + \text{mass}_{\text{rest}}\cdot\text{out}_{\text{rest}}}{\text{mass}_{\text{doc}} + \text{mass}_{\text{rest}}}\]

So: if a small cache reproduces both out and mass for the queries the model will actually ask, the document's contribution is unchanged, whatever comes after it. That is the whole objective. It never looks at the next-token loss; it works layer by layer and head by head.

2. Why each kept entry needs a bias β

Keeping fewer keys makes the document too quiet. For a query of all zeros every key scores \(e^0 = 1\), so the original mass is T while any t-entry cache gives t. A dropped-token cache therefore always under-weights the document against the question tokens. That is a weakness of the eviction methods (H2O, SnapKV, PyramidKV).

The fix is one scalar per kept entry, added to its attention score: \(e^{q\cdot C_{k,j} + \beta_j}\). Writing \(w_j = e^{\beta_j}\), \(w_j\) is "how many original keys this kept key stands for". It costs one extra number per entry, against 2 × 128 for its key and value.

A worked example. Suppose four of the document's keys are identical, \(K_1=\dots=K_4=k\), with values \(v_1,\dots,v_4\). Every query weights them equally. So keep one entry with key \(k\), value \(\tfrac14(v_1+v_2+v_3+v_4)\) and \(\beta=\log 4\):

  • mass: \(e^{q\cdot k+\log 4} = 4e^{q\cdot k}\), exactly as before;
  • output: the average value, exactly as before;
  • this holds for every possible query. With no β, the document would look four times quieter.

Real keys are not identical, so the fit is approximate and is made over a sample of realistic queries.

3. The recipe: three closed-form steps per layer and head

Fitting keys, β and values together would need gradient descent. The paper avoids it by fitting them one after another, each with a standard solver.

  1. Collect reference queries. These stand in for "the queries the model will ask later". The model reads the document, then is asked to repeat it: {doc} Repeat the previous context. {doc}, an idea from KVzip. The queries it produces while repeating are recorded. Optionally, four "self-study" prompts are added, e.g. "Aggregate all key facts mentioned in the context", and the queries produced while answering them are recorded. This gives up to 50,000 queries per head.
  2. Pick which keys to keep (\(C_k\)). Kept keys are original keys, a subset. There are two ways to choose:
    • Highest attention: score every key by how much attention it gets across the reference queries (root mean square) and keep the top t. Takes seconds.
    • OMP (orthogonal matching pursuit): greedily add the key that best fixes the remaining mass error, re-fitting the weights each time. Best quality, but minutes per context.
  3. Fit β so that the mass matches: choose weights \(w \ge 0\) minimizing \(\sum_i\big(\sum_j w_j e^{q_i\cdot C_{k,j}} - \text{mass}(q_i)\big)^2\). This is non-negative least squares. Then \(\beta=\log w\), clamped to [−3, 3] in the highest-attention variant.
  4. Fit the values \(C_v\) so that the outputs match. With keys and β fixed, the compact attention weights \(x_i\) for each query are known, and the targets are the original outputs \(y_i\). So \(C_v = \arg\min \lVert X C_v - Y\rVert^2\), ordinary least squares. The new values are new vectors, not copies of old ones.

The same steps as a sketch in code (one layer, one key/value head; the real code subtracts the maximum score for numerical stability):

# K, V: [T, d] original keys/values · Q: [n, d] reference queries · t: how many entries to keep
scores = Q @ K.T / d**0.5                      # [n, T]
attn = scores.softmax(dim=1)
keep = attn.pow(2).mean(0).sqrt().topk(t).indices     # step 2: highest-attention keys
Ck = K[keep]                                   # [t, d]

mass = scores.exp().sum(1)                     # [n]   original mass per query
Phi = (Q @ Ck.T / d**0.5).exp()                # [n, t]
w = nnls(Phi, mass).clamp(e**-3, e**3)         # step 3: "how many keys each kept key stands for"
beta = w.log()

X = (Q @ Ck.T / d**0.5 + beta).softmax(dim=1)  # [n, t] compact attention weights
Y = attn @ V                                   # [n, d] original outputs
Cv = lstsq(X, Y)                               # step 4: values reproducing the outputs

Positions. The compact cache stores t entries but keeps the document's full length T for numbering, so the question that follows gets the same positions (and rotary phases) as with the full document. Our key/value transfer already does this: kept keys sit at their original positions, and the reader counts the full length.

4. Three refinements that matter in the paper

  • Uneven budgets per head. Some heads barely care about extra entries, others need many. The paper measures this once per model, finds that the ranking of heads holds across documents and datasets, and shares out the total budget with a greedy exchange.
  • Layer by layer, "on-policy". Compacting layer 3 slightly changes the queries layer 4 produces. So layers are compacted in order, and each layer's reference queries are recorded with the earlier layers already compacted. This gives a small but consistent gain.
  • Chunks. On LongHealth, each 60k-token context of 5 patients is read in full once. Its cache is then cut into 5 chunks, each chunk is compacted on its own, and the pieces are concatenated. For our special-input handler, this means compacted entries for each document separately.

5. What it buys: Qwen3-4B on LongHealth, 1/10 size

The setup is Figure 3 of the paper:

  • model: Qwen3-4B-Instruct-2507;
  • LongHealth patients 1–20, grouped as 4 contexts of 5 patients (≈60k tokens each), 100 multiple-choice questions per context, 400 in all;
  • size = kept entries ÷ document tokens, with the chat-template tokens kept as they are.

6. Where it stops, by the authors' own account

  • Kept keys must be original keys. Only β and the values are freely fit. At extreme ratios (100×) on LongHealth, Cartridges wins, which the authors attribute to gradient descent searching a wider space. Their stated future work is "directly optimizing compact keys".
  • It matches attention, not answers. Each layer is fit to reproduce that layer's attention over sampled queries. Nothing checks that the final answer is right; small errors can add up across 36 layers.
  • The reference queries are a guess at future questions. Questions that probe a fact the repeat task never needed can miss.

7. How this plugs into our special-input handler, and how to beat it

The output of Attention Matching is exactly what our key/value handler returns for a document: per layer, t keys (unrotated), t values, and each key's position in the document. The one addition is β, which needs a per-entry, per-head bias in the reader's attention mask. Recommended arms, in order:

  1. AM through the handler (no training). Reproduce ≈0.75 at 1/10 inside our harness. This calibrates our evaluation against Figure 3 and shows that "the AC interface is compatible with prior compaction methods" with a real number.
  2. Free keys/values, Cartridges-style (the earlier plan), started from real tokens.
  3. AM start, then gradient (proposed). Start the free keys, β and values from the AM solution (≈0.75 on day one, in minutes). Then train all three end-to-end on the answer loss. This removes AM's "original keys only" limit and Cartridges' slow start. It follows the authors' future work and costs only reader-sized updates, since no encoder runs.
  4. Optional middle ground: the AM repository contains an unreported joint gradient fit (OptimJointCompaction). It adjusts keys, β and values per layer on the matching loss, with no full-model backward.

Details, data and run order are in the plan.
