Engine explainer · recommended boundary

One ensured base model can serve the base and several LoRAs

Do not replace the base vLLM object when selecting an adapter. Keep a stable adapter registry and attach one LoRA request to each chat. The current synchronous MVP should serialize lifecycle changes; real concurrent chats come with the later async engine.

  • Updated 26 Aug 2026
  • vLLM 0.28 API
  • LoRA implementation deferred

Direct answers

Question Answer MVP consequence
Can I ensure a model, then set or change a LoRA? Yes. Keep the base engine alive and register a LoRARequest containing a stable name, unique integer ID, and adapter path. Treat an adapter identity as immutable while requests use it. A changed path gets a new ID, then the old entry can retire.
Can I chat to a specific LoRA? Yes. Pass that adapter's request as lora_request. Pass None for the base model. Engine.chat(..., lora_name=None) remains the base-model path; named routing is the next slice.
Can concurrent chats use different LoRAs? vLLM can batch prompts with different per-request LoRAs, subject to its adapter limits. The present blocking wrapper uses one re-entrant lifecycle lock, so separate calls are serialized. Use AsyncLLM or a serving process for true overlap.
Can a model be freed during chat? No lifecycle transition should race an in-flight request. The synchronous MVP holds the model lock through completion. A later async design needs admission control and an in-flight counter before sleep or teardown.

The useful mental model

The base weights belong to one vLLM engine. LoRAs are request-scoped routes into that engine, not alternate base-model objects.

What belongs in this MVP

The current slice should prove the base route only. It should create vLLM lazily, accept OpenAI-style message dictionaries, disable thinking for the Qwen smoke test, return generated text, and park the model safely after the blocking call completes.

response = engine.chat(
    model_name="Qwen/Qwen3.5-0.8B",
    messages=[
        {"role": "system", "content": "You are a helpful assistant"},
        {"role": "user", "content": "Say: 'Hello, World!'"},
    ],
    lora_name=None,
)

Passing a non-null lora_name should fail clearly until registry and routing semantics are implemented. Silently falling back to the base model would make experimental results untrustworthy.

The next LoRA slice

  1. Register: map (model_name, lora_name) to an immutable LoRARequest with a unique numeric ID and normalized path.
  2. Route: resolve lora_name inside chat() and pass the request to vLLM.
  3. Replace safely: a new adapter revision receives a new ID. Stop admitting the old identity, wait for its in-flight count to reach zero, then retire it.
  4. Batch or go async: accept multiple conversations and matching LoRA requests in one vLLM call, or move the public engine to AsyncLLM.
# Later shape, not part of this implementation.
engine.ensure_lora("base", "experiment-a", "/adapters/run-42")
engine.chat("base", messages, lora_name="experiment-a")
engine.chat("base", messages, lora_name=None)  # Same engine, base route.

Limits that matter

  • max_loras limits how many adapters may be active in one batch; it is not a promise that every registered adapter stays on the accelerator.
  • max_lora_rank must cover the largest adapter rank the engine will accept.
  • Level-1 sleep is parking: weights move to CPU memory and the key-value cache is discarded. Wake restores the same engine.
  • Multiple independent blocking LLM.chat() calls are not the concurrency abstraction to build around. Batch them or use the async API.
