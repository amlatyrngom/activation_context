Typed chat, target embeddings, and side-model activations

For the pinned stack, simple typed text can go straight to LLM.chat(). vLLM 0.28 can also splice d_model-shaped rows into a chat prompt—but direct side-model activations are only meaningful after they have been aligned to the target model’s learned input space and any architecture-specific input path.

  • Completed 30 Aug 2026
  • vLLM 0.28.0 · Transformers 5.15.1
  • Live anchors: Qwen 3.5 0.8B, Gemma 3 1B, Gemma 4 E2B
  • NVIDIA L40S · all experiment clusters torn down

Direct answers

Typed text is safe; arbitrary side activations are not automatically target-space inputs. vLLM normalized string and one-part typed-text messages correctly for every tested representative. It also accepted same-shaped side rows, but a controlled 1024-wide side/target pair generated different output because the learned coordinate spaces were different.

Will vLLM throw?

Not for the tested one-part {"type":"text"} shape. Qwen 3.5, Gemma 3, and Gemma 4 were live-equal; Qwen 3 and Nemotron were normalized correctly in the metadata/template probe.

Can one user span be embeddings?

Yes. Enable prompt_embeds and send a prompt_embeds content part. Exact target rows reproduced ordinary generation for both Qwen 3.5 and Gemma 3.

Are side activations always safe?

No. This conclusion already assumes the rows have the target d_model. The remaining contract is learned basis, scale, distribution, and—for Gemma 4 E2B—a second token-conditioned per-layer embedding path.

Where does the work happen?

Tokenization is CPU work. Ordinary token embedding lookup occurs on the model’s GPU. External prompt embeddings are validated and serialized on CPU, then transferred to the worker GPU for prefill.

Live Qwen 3.5 and Gemma 3 direct string, typed text, full-prompt target rows, and hybrid target user rows generated the same greedy Hello, World! token sequence. The real project Gemma 3 engine smoke also returned Hello, World!.

Which models expect strings?

The useful question is not only what the raw Transformers template expects. It is what representation reaches that template after vLLM’s parser. vLLM inspects the Jinja abstract syntax tree: templates that iterate content parts are classified openai; the others are classified string. It then wraps or collapses text parts accordingly. Pinned vLLM renderer source.

Boundary “Accepted by Jinja” is not the same as “correct.” Qwen 3 and Nemotron demonstrated silent corruption for a user-only typed message before they demonstrated an exception. The safe boundary is vLLM’s chat renderer, not raw processor.apply_chat_template() with an arbitrary shape.

How the hybrid path works

Pinned source vLLM 0.28 defines an EmbedsPrompt for full prompts and a native prompt_embeds chat content part for interleaved spans. The latter is parsed into a reserved sentinel, expanded to one placeholder position per embedding row, and accompanied by a per-position mask. Prompt types, chat parser, hybrid renderer.

The “equivalent text” is therefore only operational:

  • <prompt_embeds> marks the splice point during template rendering. Users cannot inject that reserved literal as normal text when the feature is enabled.
  • The renderer expands one sentinel into N placeholder token IDs, where N is the tensor’s first dimension.
  • prompt_is_token_ids selects a normal embedding lookup for ordinary positions and the supplied row for embedded positions.
  • Full EmbedsPrompt inputs may also carry meaningful prompt_token_ids. That matters for an architecture such as Gemma 4 E2B, whose forward path derives additional per-layer inputs from token identity.

Minimal hybrid call shape

import base64
import io
import torch
from vllm import LLM, SamplingParams

def encode_rows(rows: torch.Tensor) -> str:
    buffer = io.BytesIO()
    torch.save(rows.detach().cpu(), buffer)
    return base64.b64encode(buffer.getvalue()).decode("ascii")

# Use the target causal model's own input embedding layer.
ids = tokenizer(
    "Say: 'Hello, World!'",
    add_special_tokens=False,
    return_tensors="pt",
).input_ids.to(embedding_layer.weight.device)
with torch.inference_mode():
    rows = embedding_layer(ids).squeeze(0).to(torch.bfloat16)

llm = LLM(
    model="Qwen/Qwen3.5-0.8B",
    enable_prompt_embeds=True,
)
messages = [
    {"role": "system", "content": "Answer exactly as asked."},
    {
        "role": "user",
        "content": [
            {"type": "prompt_embeds", "data": encode_rows(rows)},
        ],
    },
]
result = llm.chat(
    messages,
    SamplingParams(temperature=0, max_tokens=32),
)
Special-token rule: for a hybrid span, tokenize only the content with add_special_tokens=False; let LLM.chat() own system/user/assistant controls. For a full-prompt embedding tensor, prefer apply_chat_template(tokenize=True, add_generation_prompt=True). If you render text first and tokenize later, disable new special-token insertion. Transformers chat-template guidance.

Gemma 3 and an independently owned embedding module

The authenticated Gemma 3 1B run closed the earlier gate. String and typed content produced identical 22-position prompts and identical greedy output IDs. Exact target rows reproduced ordinary generation for both the full prompt and the seven-row user span.

Gemma 3 does not feed the raw table lookup into the transformer: its Gemma3TextScaledWordEmbedding applies the model's input scale. Copying get_input_embeddings() preserves that behavior; copying only the weight and performing a raw lookup does not. In the same-shape negative control, unscaled rows were accepted by vLLM but changed the generated sequence.

from copy import deepcopy

def copy_input_embedding_layer(model, device=SOURCE_DEVICE):
    # Copy the module so model-defined lookup behavior is preserved and the
    # result does not keep tied storage from the full model alive.
    embedding_layer = deepcopy(model.get_input_embeddings())
    embedding_layer.requires_grad_(False)
    return embedding_layer.eval().to(device)

def extract_input_embedding_layer(self, device=SOURCE_DEVICE):
    starting_device = self.current_device
    if starting_device == FREE_DEVICE:
        self.to_device(SOURCE_DEVICE)
    try:
        return copy_input_embedding_layer(self.model, device)
    finally:
        if starting_device == FREE_DEVICE:
            self.to_device(FREE_DEVICE)

Live The copied module was frozen on CPU, produced rows exactly equal to vLLM's scaled rows, and remained usable after the full Transformers model returned to the free sentinel. A model that begins already loaded is left on its starting device. The helper intentionally does not choose a permanent CPU/GPU pinning policy.

Compute and placement

Embedding lookup is a row gather, not another transformer forward pass. For ordinary text, vLLM already performs this lookup inside the GPU model. Converting text to embeddings outside vLLM adds serialization and transfer without changing the model’s computation, so it is worthwhile only when the rows are already modified or produced by another component.

Gemma 4 E2B exception: its primary table is only part of the token-input state. The checkpoint also contains a 35-layer, 256-wide per-layer embedding table: 2.35 billion parameters, or 4.38 GiB in BF16. Main plus per-layer token embeddings account for 53.71% of that checkpoint. The audited Gemma 4 12B, 26B-A4B, and 31B configs do not declare this PLE table.

Pinning conclusion. For the requested 8B–32B fixtures, the main table is 1.16–2.62 GiB and 2.37–10.54% of the checkpoint. Keeping it resident is reasonable on a 48–80 GiB GPU when it is a hot-path component and that headroom is intentional. On a 24 GiB deployment—or whenever KV cache/model placement is tight—CPU residency or on-demand placement is a real tradeoff. Do not infer the decision from percentage alone.

CPU versus GPU choices

  • Normal text: CPU tokenization, then vLLM’s resident GPU embedding layer. This is the cheapest path.
  • External adapter rows: compute wherever the adapter lives, but expect vLLM 0.28 to move/keep the incoming tensor on CPU for process serialization and then transfer it to the GPU worker.
  • Text converted outside vLLM: a separate Transformers model duplicates weights; a CPU embedding table avoids a second GPU model but still consumes substantial host RAM. Neither is needed when the text could remain token IDs.
  • Resident extraction: the experiment used LLM.apply_model() only to prove exact equivalence without loading duplicate weights. vLLM itself documents that API as control-plane oriented, so it is not the recommended production data path.

Final side-activation verdict

Direct side-model activations are not always safe, even when they already have the target d_model. vLLM is a tensor carrier, not a learned-representation validator. A side model must be trained or projected into the target's actual input space, then validated against that target family and architecture version.

A Gemma 4 E2B smoke with main rows alone happened to emit the same five output tokens for this short prompt, but the internal path was not equivalent: hybrid sentinel positions select a fallback token for PLE. A full EmbedsPrompt with meaningful companion target token IDs preserved the token-conditioned path and matched the text baseline. One matching output is therefore not evidence that E2B's PLE can be ignored.

Pinned source vLLM requires enable_prompt_embeds=True, validates rank/width/floating dtype, and forces tensors to CPU for inter-process serialization. The feature is explicitly trust-gated because malformed embeddings can crash an engine. Deserializer validation, renderer device handling.

Recommended next implementation slice

  1. Let vLLM own ordinary message normalization. Pass string and typed text into LLM.chat(..., chat_template_content_format="auto"). The authenticated Gemma 3 run removes the former gate-based fallback concern.
  2. Widen the engine message contract. Admit a trusted prompt_embeds content part; do not run it through the current text-only assertion in adapt_message_format().
  3. Enable the feature only on engines that need it. Set enable_prompt_embeds=True at LLM construction and treat callers as trusted.
  4. Keep special-token ownership singular. Full-prompt rows come from a tokenized chat template; hybrid rows come from content-only tokenization with special tokens disabled.
  5. Use the staged primary-module helper as a building block. Decide CPU/GPU pinning at the caller after considering the measured 1.16–2.62 GiB large-model range.
  6. Train the side-to-target interface. Treat a projector/adapter and its family-specific validation as part of the model, not as optional transport glue. Give Gemma 4 E2B an explicit PLE policy.

The current is_multimodal-based adaptation happens to align with several ordinary-text templates, but it is the wrong capability boundary. vLLM’s template detector is more precise, and the current non-multimodal assertion would reject a valid prompt_embeds content part before vLLM can parse it.

Operational notes

  • Prefix caching includes a SHA-256 hash of each block’s prompt-embedding bytes, so cache identity follows the actual supplied rows. Pinned cache-key source.
  • Upstream vLLM 0.28 tests cover multiple and adjacent embedded spans, both string and OpenAI content templates, output streaming, and greedy text/embedding equality. Official end-to-end tests.
  • Output streaming is supported. vLLM’s separate resumable streaming-input API rejects prompt_embeds chunks.
  • Qwen 3.5 happened to produce identical user IDs with add_special_tokens=True and False; that is tokenizer-specific and is not a reason to relax the cross-model rule.
  • The staged Sky wrapper sends an existing project `.env` through sky exec --secret-file while `.skyignore` keeps the file out of the exact rsync mirror. The live job observed the variable and confirmed the mirrored file was absent; no value was printed.
  • Remote wrapper commands set VLLM_WORKER_MULTIPROC_METHOD=spawn. Without it, the real Gemma 3 engine smoke hit CUDA's “cannot re-initialize after fork” guard; with it, the same project path completed normally.
  • The implementation is staged, not written into the user's read-only source: one updated Sky wrapper and one embedding helper/lifecycle method. The experiment-specific ac-embed-next cluster was deleted after retrieval; final Sky status showed no clusters, jobs, or services.

Method and limitations Versions, run boundaries, and evidence gaps Optional

Run shape

The first cloud run classified templates and loaded Qwen 3.5 0.8B for generation/performance checks. The follow-up reused one disposable L40S node sequentially for authenticated Gemma 3 1B, the Qwen 3 Embedding 0.6B → Qwen 3.5 0.8B controlled transfer, Gemma 4 E2B, and the real project engine smoke. Sampling controls were greedy for equality checks.

Instrumentation retry

The first engine run completed direct chat, then stopped because apply_model() would not serialize the self-authored measurement callback. The successful rerun set VLLM_ALLOW_INSECURE_SERIALIZATION=1 solely for that trusted diagnostic callback. The flag is not required for prompt_embeds, chat normalization, or the proposed product path.

Version boundary

Findings are pinned to vLLM 0.28.0, Transformers 5.15.1, and the exact model revisions recorded in the evidence. Gemma 4's public family is not one uniform input architecture: E2B has the measured PLE path, while the audited 12B/26B/31B configs do not. New variants or revisions should be re-audited before the paper claims equivalence.
