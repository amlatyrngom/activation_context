Activation context in the agent loop: the rules as I read them

Every AC channel uses one contract: messages carry ordered text and activation-context parts; the target tokenizer renders a part as a run of placeholder tokens; the AC model turns the part into rows; the engine gets token ids plus rows; the run result keeps parts and spans, never rows. The four channels, the compaction protocol and the two open protocol questions are below. The plan itself is SLICE3B_PLAN.tressoir.md.

5. Accepted (2026-09-09)

Channels and protocol: agreed as drawn ("though reverify just to be sure"). Reverified on CPU with the tiny Qwen3.5 fixture and the 3a1 part tokenizer (IB/TMP/SLICE3B/reverify_shapes.py): consecutive user messages render, placeholder runs match the requested rows, a second compaction nests the first tree verbatim, the child prompt and a tool result with a part tokenize with one span each, and the current continuation wrapper flattens parts away (so the dialect change in the plan's M2 is required).

Child's returned segment: your note, "yes, but with recursive compactions to condition the compression", is the drawn behavior made explicit: the returned part is the child's final segment, whose first user message holds the child's compaction tree when it compacted, so the compression is conditioned on the whole child history.

Absolute cap: the run ends with finish_reason="trajectory_cap", recorded like context_exceeded, never raised.
