# Large-run implementation and launch readiness

The implementation prepares one coherent training pass from committed data, including recursive conditioning and two- or three-input targets. CPU checks, two independent scoped reviews and the actual two-H200 launcher pause/resume test have passed. Hardware scaling checks remain pending; this is not yet a claim that every configuration meets the speed target.

## What changed

The existing trainer can distribute a logical batch of eight across two or four GPUs on one node. It balances actual recursive encoder and reader work, sums globally normalized gradients before clipping and Adam, coordinates stopping and errors, and gives reporting and checkpoint publication one writer. Plain agent SFT leaves unused encoder parameters without gradients. Native checkpoints retain optimizer state, penalty sampling and per-rank RNG; exact distributed resume currently requires the same GPU count. Abrupt preemption can replay work since the latest committed checkpoint; planned stops use the native paired-save path.

The study builder now supports question-aware, question-blind and recursive parent-context QA using existing AC parts. Recursive reconstruction retains its literal gold targets and a controlled final row budget. Multi-target construction combines two or three independent contexts, numbered requests and responses separated by `---`; it preserves nested parts and their ratios. The initial recipe assigns about10% of each AC task family to groups, preferring shorter intact sources and limiting grouped full-context-plus-target reader views to24,576 tokens for familiarity training. Oversized groups fall back to two inputs or singles without truncating evidence.

Portable-bank snapshots bind committed text files and their split controls. They remain readable independently of source code and synthesis-cache identities. The mixed runner records the actual available selections, unique source counts, grouped examples, targets and loss weights. CPU preparation persists compact native examples, which GPU attempts load once rather than rebuilding per rank. New prepared examples also cache their scheduling-cost estimates; older caches remain readable through the original calculation. The preparation receipt also records the enforced reader/encoder capacity bounds. GPU attempts skip repeated recursive capacity validation only for the exact cached objects when both loaded model capacities support those bounds; new/reference views, older receipts and smaller or unknown capacities use native validation. Focused native checks passed. Together these changes avoid repeating full-bank tokenization on every GPU rank.

The launcher checks the whole storage-quota domain, filesystem headroom and CPU memory before placement. It uses the actual Slurm allocation end, stops through the native paired-save path and requeues duration-limited attempts. Partial and completed checkpoint markers are authoritative; protected pairs and previous recoverable state survive pruning and interrupted publication.

## Training recipe

Initial working budgets are100k RAG questions,100k trajectory questions,32k summaries,20M plain-agent assistant targets and10M reconstruction rehearsal targets, using whatever committed data is available. Working loss shares are25/25/25/15/10. QA conditioning is40% direct,40% recursive-parent and20% uncontextual summarization. Task ratios sample uniformly from1/20 to1/10; reconstruction uses1/30 to1/10. Main held panels use1/16.

The separate reconstruction warm-up remains110,177,607 original targets. Its paused native checkpoint has already trained32,176,070 targets across51,672 passages. CPU job23903398 committed preparation of all124,184 remaining passages:107,986 training examples, including10,799 short multi-target groups, with about30M original targets assigned to recursive layouts. The older unstarted preparation was cancelled. It preserves Adam/RNG and global update offset6,459; the new phase has its own local step zero and an explicitly revised cosine horizon. Original held examples remain intact, with separately labeled recursive and multi-input diagnostics. This is pre-mixing work, not a new mixture weight.

Each prepared run owns `report.tressoir.html` and `report_data.json`. The HTML is installed once; live updates change JSON and existing DOM cells, preserving scroll and focus. Multi-input and recursive diagnostics have separate rows. No-context and full-context controls use the frozen reader from the start of that phase.

## Validation and limits

Private checks cover the actual tiny training loop on1/2/4 CPU ranks, native pause/reload, penalty decisions, unused-gradient Adam behavior, published checkpoint recovery, portable-bank integrity, recursive target preservation, multi-target construction, actual-tokenizer capacity fallback, resume offsets and cached-example identity/tamper rejection. Two independent reviewers identified issues; the affected fixes passed narrow re-review. The report's JavaScript and stable-DOM updates also passed focused checks.

Real H200 experiments found that an unchanged one-GPU repeat diverges after several BF16 updates: first-gradient relative error was1.46% for the encoder and0.90% for the reader; the corresponding one-versus-two-GPU values were1.66% and0.91%. Initial objectives, weights, penalties and reference hashes matched, and the measured NCCL sum was correct. Consequently, the hardware gate compares objectives and gradients at fixed weights under the existing tolerances, separately from genuine sequential-Adam timing. This does not establish deterministic replay or isolate the noisy kernel.

The actual two-H200 launcher test2319413 passed:28 grouped examples covered40 family-qualified source items exactly once. It paused after one global update and restored native Adam plus both ranks' CPU/CUDA RNG before completing three more. Penalty RNG matched the committed prefix, frozen controls and the main HTML hashes stayed unchanged, and reported peak GPU memory was45.76GiB. The allocation lasted6m26s. This is runtime/recovery evidence, not convergence or scaling evidence; receipts are in `IB/TMP/FIRST_TASK_AWARE_FINETUNING/mixture_runtime_gate_v1/`.

Checkpointing every reader forward fixed that capacity failure; the successful two-GPU test peaked at124.42GiB. The optional cost-ordering candidate failed one encoder-gradient comparison at7.817% relativeL2 against the unchanged5% limit, despite identical objectives. Its failed batch contains seven plain-agent items and one encoder-bearing reconstruction item, so across-example encoder accumulation cannot explain that discrepancy. The separate original-order four-GPU attempt stopped earlier: its unchanged native one-GPU repeat failed at5.272%. No canonical four-GPU speed is claimed. A bounded diagnostic excluded accumulation and reduction: all trainables and incoming gradients are FP32, and the single encoder-bearing example already contains the discrepancy. Strict Torch/cuDNN determinism with a pre-start cuBLAS workspace made native repeated encoder and reader gradients exactly equal on that isolated batch. This identifies a working execution setting, without identifying the individual responsible operator. Thresholds are unchanged and the original failures remain recorded.

A new opt-in `deterministic` training setting scopes strict PyTorch/cuDNN controls and restores prior flags after success or failure. CUDA requires `CUBLAS_WORKSPACE_CONFIG=:4096:8` (or`:16:8`) at process startup. Training and standalone evaluation use the same scope before autotuning; disposable autotuner workers receive the effective mode at startup and bind it into profile identity. Focused CPU review passed native train/eval, nested and exception restoration, workspace guards, CLI overrides and append-only attempt provenance. The full strict two-H200 test completed. Native repeats match exactly across all108 examples and14 optimizer steps, and fixed-weight one-versus-two-GPU gradient error is only about6.6e-8. However, repeated optimizer steps diverge substantially between one and two GPUs: maximum loss difference0.08641 and final encoder-update relativeL2 about1.03. The follow-up diagnosis resolved the cause without changing precision or tolerances. The first update changes weights only at FP32 rounding scale; replicas remain bitwise identical. Transplanting the two-GPU post-update weights and Adam state into native one-GPU training reproduces the next loss, penalties and frozen references exactly, and reduces gradient differences to about6e-8. The large later drift is therefore sensitivity to the initial summation-roundoff perturbation, not a distributed objective or optimizer mismatch. An independent source audit found no lifecycle defect. This clears the distributed-semantics blocker, while preserving the evidence that trajectories at different GPU counts are not numerically interchangeable. Hardware throughput checks can continue; no large mixed run has started. Evidence: jobs2337838 and2338512 under `IB/TMP/FIRST_TASK_AWARE_FINETUNING/strict_{first_updates,step1_transplant}_v1/`. Strict timing was13.397s on one H200 versus7.699s on two (1.740×); memory peaked at124.42GiB. The strict native mode costs about35% versus the earlier mode. No thresholds changed. The mixed launcher sets the workspace before torchrun; `CHANNEL_DETERMINISTIC=1` opts in, while omission preserves the prepared recipe.
