# Separate reader checkpoint threshold: bounded candidate

The frozen trainer can already apply separate encoder and reader thresholds. Its public resolver currently returns the same threshold for both (`activation/autotuners/__init__.py:44–58`), and `train()` installs them independently (`ac_model_training.py:494–508`). A private probe can keep the encoder at0 and set the reader to4096 by wrapping the existing runtime-variable method. No product change, new configuration type, packing change or precision change is needed for the measurement.

**The initial1700 suggestion skips too little reader work; the single candidate is4096.** Roughly500 compressed rows are only part of the reader input. In the exact saved8k cases, complete reader sequences are747–1026 tokens. The reader gate counts **microbatch size × padded length**, whereas the encoder gate uses its maximum sequence length (`ac_model_training.py:1202–1205`, `ac_model.py:528–532`). At microbatch2, threshold1700 disables only one of four AC forwards in the saved failing batch, and none in the saved quantile batch. Short no-context penalty forwards do fall below1700. A4096 threshold exceeds the chosen batch’s reader microbatches (maximum2×1004=2008), so it disables all reader recomputation in the chosen case; larger inputs can still checkpoint. This is a batch-specific execution test, not a claim that every long-context reader can run without checkpointing.

The original failing-case diagnostic recorded reader shapes2×803,2×961,1×452,2×975,1×463,2×1004,1×495: seven forwards and seven first-layer recomputations. Threshold1700 should remove four of those recomputations, representing3016/8896 padded reader positions for that penalty draw. This is a reader-forward work proxy, not a measured wall-time saving. The broader three-update memory trace has about27% of reader positions below1700 in the failing case and about11% in the quantile case. Encoder/heads work is unchanged. Earlier original-path memory fits took about23–25s per eight questions and49.8–52.3GiB peak; those measurements were P2-weight fits, not the proposed mature-Adam A/B.

`bench/probe_reader_checkpoint_v1.py` reuses the guarded strong32k final pair/Adam4000 loader and exactly the old failing logical batch's eight questions and8k inputs. It measures **reader0 versus reader4096 only**, keeping encoder0,65536 packing, original masks/precision, micro2/logical8, loss/baseKL, seed and actual penalty IDs fixed. There is no new training arm or saved model.

1. A deterministic diagnostic process compares baseline, unchanged repeat and reader4096. It captures all AC outputs, reader gold-token log probabilities, joint loss and all630 trainable entries (615 active gradients). Existing3% relative-RMS/2e-6 absolute-floor tensor gates and1e-3 absolute joint-loss gate remain unchanged. First-layer hooks must prove encoder recomputation persists and reader recomputation follows the exact observed batch gate. Failure stops the controller before timing. The candidate must show zero reader recomputations and retained encoder recomputations in every microbatch.
2. Two fresh ordinary-kernel processes each reload the same saved pair and Adam4000, then run one warmup plus three updates at the unchanged terminal LR. Parameter steps advance only in memory to4004. Exact penalty IDs, inputs, padding and source hashes must match; both report step times and peak memory. Production timing does not enable deterministic flags. Successful and failed proof paths rehash the original parent pair/optimizer; nothing writes them.

The current95GiB RTX has plausible headroom versus observed production peaks near53.6GiB, but there is no defensible static bound for the additional saved reader activations. An OOM stops the trial without a fallback setting or changed acceptance gate.

One15min RTX allocation with64GiB host and840s controller budget should cover the three processes; a timeout is incomplete evidence. Do not adopt the setting from a partial result or claim a whole-run speedup from one batch. No staging, GPU submission or active-source change has occurred. The CPU/metadata validation receipt accompanies the candidate; actual9B-model equivalence and performance remain unmeasured.
